# GitLab domain mapping: standalone issues, body blockers, pipeline jobs as status checks

GitLab joins GitHub as a second Forge (ADR 0042) with **full lifecycle parity** as the design target — reconcile, implement, merge request, pipeline watching, merge, close — delivered in phases. Parity is reached by mapping GitLab onto the existing GitHub-shaped domain rather than extending it. Every open Ready-labeled GitLab issue reconciles as a **Standalone Issue** — no Parent/Child, no Implement All — because issue hierarchy and blocking links are paid-tier GitLab features an instance cannot be assumed to have; Listed Blockers are instead parsed from a `Blocked by: #n` body line, so Queue and Waiting for blockers still apply, and closing-PR ownership ports unchanged via `Closes #iid`. A **PR Status Check on GitLab is one job of the pull request's head pipeline** — a failed `allow_failure` job is not red, and manual or canceled jobs never trigger a handoff — so Watch, Check-Start Anchors and Deadline, Status Check Handoffs, and retry operate unchanged; GitLab has no required status contexts, hence no Expected PR Status Checks. GitLab issues and merge requests use separate per-project number sequences, unlike GitHub's shared space, so harness code must not treat one number as unambiguous across the two kinds. GitLab credentials resolve **vault-first** when Keymaxxer is enabled: a per-Repository vault secret (`provider: gitlab`, `account: <forge-host>/<project-path>`, suggested name `GITLAB_TOKEN_<HOST>_<PATH>`) is strictly more specific than ambient `GITLAB_TOKEN` / `glab`, matching the GitHub layer's vault-first precedent. Vault-credentialed Forge operations run through token-injected helper processes so the raw token never enters the Harness or Agent Turn environments. When no vault secret exists, ambient credentials remain the fallback: `GITLAB_TOKEN` or `glab` for reconciliation and host-authenticated `glab` for Agent Turns. Adding the vault credential activates Issue Polling; removing it leaves ambient (if any) or suspends polling when neither source remains. Agent Turns use `glab`, never `curl` or `gh`, preferring `keymaxxer_run` with the named secret mapped to `GITLAB_TOKEN` only inside the child process when the vault holds one. `curl` remains contributor tooling for monorepo fixture scripts and is not a product host tool.

**Considered Options.** Probing the instance for paid-tier features before deciding was rejected: it designs for capabilities most GitLab instances lack, and the body convention matches how Drupal.org issues already reference each other. Emulating hierarchy through markdown task lists was rejected: task lists on Drupal.org are checklists, not sub-issues, and the parsing would invent semantics the platform does not have. Treating the whole pipeline as one status check was rejected: it collapses every failure into one blob and loses per-job accumulation and the staggered-settle behavior Watch relies on. Ambient-only credentials (no Keymaxxer) remain valid when Keymaxxer is disabled. Vault-only without ambient fallback was rejected: GitLab operators often already have `GITLAB_TOKEN` or `glab` and should not be forced onto the vault for every Repository.
