# Open an OpenCode Session in the web UI

OpenCode Sessions are opened from the Session usage dialog, not from an inline action on Work Item cards or list rows. Clicking the Session ID still opens usage. For an eligible OpenCode Session the dialog footer offers Open in OpenCode instead of Show tail. Other Agent Backends keep Agent Turn Tail. OpenCode without a Session ID or a resolvable server falls back to that tail when the backend can serve one.

The launch is an operator click, not a link rendered with the Work Item. The click asks the harness for a one-time connection to the same OpenCode server the agent and telemetry use, then opens that Session in a new tab. A fresh browser does not paste a pairing link, scan a QR code, or type a password. A browser that is already paired still lands on the same Session.

Verified on OpenCode 2.0.32: `POST /api/pair` requires the server's existing authentication and returns a single-use code that expires in five minutes. `GET /auth/connect/{code}` with an HTML accept sets an HttpOnly `SameSite=Lax` session cookie and redirects to `/`, not the Session. The harness therefore navigates the new tab to that connect URL and, once the browser has committed to the OpenCode origin, navigates the same tab to `<server-base>/server/<base64url(server-base)>/session/<encoded-session-id>`. The pairing code is not stored, is not minted while listing or polling Work Items, and is not a reusable password. The new tab drops its link back to the harness before it leaves the harness origin. If pairing fails before that navigation, the dialog shows a bounded reason and the blank tab is closed. Once the tab has reached OpenCode, the harness cannot read the page. A grant that fails only after that navigation can still show OpenCode's own error page; it does not open a different server.

The server address is resolved on the backend, never by a command from the browser, and is not hardcoded. When Keymaxxer is enabled, the address and basic-auth header are the harness-owned OpenCode server ([ADR 0078](0078-harness-owned-opencode-server.md)). That handoff never falls back to the shared service, including after the owned server restarts or becomes unavailable. Otherwise an explicit server configured for the agent wins (`READY_FOR_AGENT_OPENCODE_SERVER`, or the application option). Its password is `OPENCODE_PASSWORD` in the harness process, kept in memory and sent only as the pair request's basic-auth header. When neither is set, the harness uses the same shared-service discovery and registration credentials as telemetry. It does not start the shared service. The discovered or configured address is used as-is, including localhost when the browser and service share a machine or an SSH port forward. The harness origin is not substituted for the OpenCode origin.

GraphQL list data and the dialog query expose only whether the action is available. They do not contain the pairing code, the server password, basic-auth material, service-registration credentials, or the Keymaxxer capability URL. Those values are also kept out of ordinary links, persistent settings, logs, and operator-facing errors. OpenCode authentication is not disabled, and the user's shared service is not reconfigured.
