# Harness-owned OpenCode server when Keymaxxer is enabled

OpenCode 2 applies `OPENCODE_CONFIG_CONTENT` when the server process starts. A CLI client's environment is not forwarded to an already-running shared background service, so injecting the Keymaxxer sidecar capability URL on `opencode run` or `opencode api` does not configure that service. Model discovery that used `--standalone` saw the override; agent turns and session API calls did not.

While Keymaxxer is enabled, the harness runtime starts one private OpenCode 2 server and routes every harness OpenCode operation to it: runs, session creation and continuation, configured commands, model switching and discovery, wait, interrupt, and export. Worktree routing stays on the command (`PWD` / process cwd for `run`, `x-opencode-directory` for API calls). The server is reused for concurrent turns. It is started with `opencode serve --hostname 127.0.0.1 --port <ephemeral>` and the existing sanitized environment, including the forced remote Keymaxxer MCP override. `--service` is not used, so the user's shared service is not started, stopped, restarted, or reconfigured.

Verified on OpenCode 2.0.32: the server password is `OPENCODE_SERVER_PASSWORD` (basic auth username `opencode`); CLI clients need `OPENCODE_PASSWORD` with `--server`. `run` accepts `--server` before the subcommand. `api` and `session export` accept it only on that command, not as a flag before `api` or `session`. Both the password and the capability URL stay in memory. They are not written to configuration files and are redacted from operator-facing errors. Readiness is an authenticated config read that contains the capability URL. If the server cannot start, or it exits later, OpenCode operations fail with an actionable error and do not fall back to the shared service. The rest of the harness still starts so other Agent Backends remain usable. Application dispose stops the owned server.

When Keymaxxer is disabled, the harness starts no owned server and keeps the previous connection: default shared-service discovery, an explicit server when one is configured, and `--standalone` model discovery.
