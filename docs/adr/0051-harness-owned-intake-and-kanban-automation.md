# Harness-owned Intake and Kanban automation

Finite operator automation lives in the published `ready-for-agent` CLI, but lifecycle-rich behavior remains owned by the running Harness and is reached through GraphQL. The Harness classifies Intake Candidates, performs synchronous best-effort Repository Intake, and projects the six Kanban lanes; the CLI validates repository identity and emits a versioned JSON envelope. The visual Kanban consumes the same server projection as CLI status so lane meaning cannot drift between clients.

Repository Intake is deliberately an operation rather than a persisted aggregate: it has no Intake ID, membership, history, explicit cancellation command, concurrency setting, scheduler, or status. It snapshots current candidates, processes them sequentially through ordinary Implement Now or Queue behavior, and returns one result per Issue; successful Work Items remain when another candidate fails or HTTP request cancellation interrupts processing. Candidate listing and Intake use the current Issue projection without refreshing it, and each invocation reclassifies current state rather than applying a prior plan.

All finite operator commands, including `add`, emit one versioned JSON document. `start` remains a long-running process with ordinary logs. GraphQL domain failures retain stable `extensions.code` values in CLI error JSON; partial Intake is a result document with a nonzero exit, not a hidden GraphQL failure. The default loopback GraphQL endpoint and explicit remote endpoint override remain trusted operator surfaces; authentication is a separate Harness-wide concern.
