# The lifecycle model is derived from a versioned ontology

The harness's domain model exists twice: once as prose in `CONTEXT.md`, and once as imperative code — and the two are enforced nowhere against each other. The Work Item state space is declared four times (three Drizzle column enums, an Effect Schema literal union, and the GraphQL SDL enum), while the transition relation is not declared at all: `nextOperationalStep` gives only the happy-path successor and roughly thirty other transitions live as `nextState` literals inside step-handler decision trees, applied through about thirteen hand-written `UPDATE work_item SET state` statements. Shared predicates are duplicated with diverging definitions — "at most one unfinished Work Item per Issue" has three (the partial unique index excludes `needs_human` from unfinished, `createWorkItem` includes it, `isTerminalWorkItemState` counts it terminal), and Implementable Issue is written four times with three failure vocabularies, including a UI re-derivation. Agent-reported Outcomes cross into the harness through six independent regex sentinel parsers with no schema, even though Forge API responses are Schema-decoded. Following `docs/why-agentic-systems-need-ontologies.md`, the harness adopts an explicit machine-readable ontology as the single source of truth for the domain model, with the runtime artifacts generated from it.

The ontology is a small custom `rfa:` namespace authored in Turtle under `ontology/`: `rfa.ttl` for classes, properties, derived-class definitions, and disjointness axioms, and `shapes.ttl` for SHACL contracts. Every `CONTEXT.md` term maps to a SKOS-annotated class or property (`skos:prefLabel`, `skos:definition`, each `_Avoid_:` entry a `skos:hiddenLabel`), so the glossary is generated from — or at minimum diffed against — the ontology rather than maintained in parallel. Predicates that are duplicated today become OWL class expressions with exactly one definition (Leaf, Implementable, Actionable, Relevant, Unfinished). Prose-fought confusions become disjointness axioms (Repository Paused vs Pause Work Item, Waiting for blockers vs Admitted, the pairwise-disjoint terminal states). The transition relation becomes first-class `rfa:Transition` individuals carrying `fromStep`, `toStep`, guard, and a reason code from the existing `STEP_RUN_REASON` vocabulary; per-step properties (agent-free, max duration, retryable) attach to `LifecycleStep` individuals, generalizing `agent-free-steps.ts` and `DEFAULT_LIFECYCLE_MAX_DURATIONS`. PROV-O covers the execution side (`StepRun` and `AgentTurn` as `prov:Activity`, `AgentBackend` as `prov:SoftwareAgent`, outcomes attributed to agent or harness), making "who decided this" a standard query.

The ontology does not run in the hot path. A codegen step derives a `lifecycle-model` package — state enum, step list, transition table, step-property maps, and shared predicate functions with one failure vocabulary — consumed by the Drizzle schema, Effect Schema literals, GraphQL SDL, lifecycle service, and UI. Reasoning and SHACL validation (N3.js plus `rdf-validate-shacl` under Bun) run in CI over ontology consistency and a corpus of valid, invalid, and contradictory example instances. At runtime the single transition-application point asserts that every applied `(fromStep, toStep)` pair exists in the generated relation. Adoption is phased: formalize the ontology and CI first with no behavior change; then point the four enum declarations at the generated module; then consolidate the shared predicates and align the unfinished-Work-Item unique index with the ontology's definition; then replace the six sentinel parsers with per-step Agent-reported Outcome schemas whose prompt contract sections are generated from the same declaration, with the controller overwriting all identity fields (Work Item, PR, Issue) from harness records before an outcome enters transition selection; and finally restructure step completion into proposal → relation check → guard predicates → invariants → one transactional commit, collapsing the scattered state updates and Worker Slot releases into declared transition effects.

**Considered Options.** Keeping the model in TypeScript only — an ontology-as-code data structure without RDF — has zero impedance with the codebase but forfeits standard tooling: no reasoner to prove the derived classes consistent, no SHACL corpus testing, no SKOS link to the glossary, and the model remains legible only to this codebase. Running a live SHACL validator inside the lifecycle hot path was rejected as buying latency and a dependency rather than safety; the generated table lookup and the aligned database constraints are the enforcement, per the source article's separation of semantic model from storage and enforcement engines. Reusing a public vocabulary wholesale was rejected — nothing covers an agentic engineering harness — but SKOS and PROV-O are grafted on where they genuinely fit. A big-bang rewrite of `work-item-lifecycle.ts` was rejected in favor of the phased path, with the runtime relation assertion landing early so real traffic reveals any transition the declared model missed before the invasive restructuring begins.

**Consequences.** `ontology/rfa.ttl` and `ontology/shapes.ttl` become versioned production interfaces; domain changes start with an ontology edit and flow through codegen, so the four state-enum declarations can no longer drift. The `work_item_one_unfinished_v2_uidx` index changes to include `needs_human` as unfinished, matching `CONTEXT.md`. The agent contract changes from sentinel lines to one JSON outcome object per step, decoded with Effect Schema and retried through the existing structured-feedback path. CI gains an ontology job; the build gains a codegen step. The ontology stays scoped to the terms in `CONTEXT.md` — the smallest domain in which an agent can cause material harm — to avoid recreating the expert-system knowledge-acquisition bottleneck.
