# Claude Code Agent Backend

Claude Code is the fourth built-in Agent Backend, with stable ID `claude` and operator-visible label **Claude Code**, delivered as a `packages/claude` adapter on the shared `@ready-for-agent/agent-backend` contract (ADR 0031), following the Grok and Codex adapter shape. Turns run as headless `claude -p` (print mode) with `--output-format stream-json` (plus any flags required for terminal result events, such as `--verbose`); the adapter normalizes the stream to ordered final assistant text and success/failure. The Session ID is a Harness-generated UUID preassigned on the first turn with `--session-id <uuid>` and continued across turns and Harness restarts with `--resume <uuid>`. Directory-scoped `--continue` and resume-forking `--fork-session` are never used (they race under concurrent Work Items or mint a new Session). The `/review` Agent Command is prompt-prefixed, as in the Grok and Codex adapters. Authentication is ambient (`claude auth login` / OAuth, or `ANTHROPIC_API_KEY`), with ambient `gh` for Agent GitHub Access and no Keymaxxer integration; readiness inspection is binary presence plus non-interactive `claude auth status` (JSON, exit 0 when logged in). Harness Config default remains OpenCode; selecting Claude Code is optional per harness default or Repository override (ADR 0037).

Deliberate design choices that are part of this decision:

- **Headless Claude Code CLI only.** Integration is the shipped `claude` binary under the ADR 0031 CLI adapter contract—not the Agent SDK, ACP, a long-lived Claude server process, or operator-defined commands. Project-instruction conventions stay backend-native (`CLAUDE.md` and related discovery in the Work Item worktree).
- **Preassigned Session ID.** ADR 0031 requires the Session ID while the first turn is still running. Capture-only from a final JSON envelope fails that requirement if the process dies mid-first-turn. Preassigning a UUID (Grok-style) satisfies the contract without depending on early stream events for identity.
- **Model catalog by provider mode.** First-party Claude Code keeps an adapter-bundled static catalog of floating aliases `haiku`, `sonnet`, `opus`, and `fable` (Anthropic resolves each alias). Excluded: `default`, `best`, `opusplan`, and context-window variants such as `sonnet[1m]` / `opus[1m]`. When Claude Code reports authenticated Amazon Bedrock, that static alias catalog is **not** offered; the Agent Model catalog is instead active Anthropic-backed Bedrock inference profiles discovered via the AWS SDK `ListInferenceProfiles` control-plane API (ambient harness process credentials and region — not the AWS CLI executable). The production package bundles that AWS SDK discovery path on every supported compile target; host preflight never requires `aws` on `PATH`. Region resolution prefers `AWS_REGION`, then `AWS_DEFAULT_REGION`, then the active named profile’s region in shared AWS config, then remaining SDK defaults. The catalog includes both **system-defined** profiles (persisted Agent Model value = inference profile ID) and organization **application** profiles (persisted value = ARN). Optional operator-facing `name` and `kind` (`SYSTEM_DEFINED` / `APPLICATION`) travel on Agent Model transport for Settings presentation; other Agent Backends omit them. Catalog entries retain the Claude Thinking Levels. Discovery is best-effort and non-fatal for readiness: a successful Claude readiness probe stays Ready when listing fails, with an empty or partial catalog and an actionable warning on Active/Preview/Recheck status that distinguishes common AWS causes without exposing credential material (issues #820 / #821 / #822). **Operator-facing Bedrock Settings mode** is selected by harness process `CLAUDE_CODE_USE_BEDROCK=1` (exact value only): GraphQL `agentBackends` exposes label **Claude Code Bedrock** and `configurationMode: bedrock` so the browser never reads process env (issue #828). In that mode Harness Config and Repository Settings offer discovered profiles only. Existing saved values are never auto-deleted or rewritten; unavailable values are shown until the operator picks a current profile. Ready/Unavailable still come from Claude authentication inspection, not from the env flag alone. `bedrock:ListInferenceProfiles` is optional catalog IAM only and does not prove `InvokeModel` entitlement. Recheck and Preview refresh provider, catalog, and warnings atomically; discovery is bound by the inspect timeout. This supersedes the earlier Bedrock free-text fallback product decision. Vertex, Foundry, and other third-party deployment IDs remain out of catalog in this adapter.
- **Catalog-only Agent Model selection (issue #838).** Agent Model selection is catalog-only for **every** Agent Backend—OpenCode, Grok Build, Codex Build, first-party Claude Code, and Claude Code Bedrock—in both Harness Config and Repository settings. Build and review model controls are real selects over the current catalog; there is no editable input, `<datalist>` suggestion, or free-text entry anywhere. This **supersedes the first-party Claude free-text decision of issue #806** while retaining the strict Bedrock decision of issue #828. A stored value the current catalog does not list is preserved and shown as a visibly unavailable option alongside the current catalog—never silently deleted, rewritten, translated between provider modes, or coerced to the first catalog entry—and Save stays blocked until the operator picks a current model or (Repository scope) clears the override back to inheritance. Save is likewise blocked while a catalog is loading, failed, or empty, because membership cannot be established. Enforcement is not browser-only: `updateConfig` and `updateRepositorySettings` validate every explicit model against the catalog of the backend the mutation is about to make selected/effective (current status when Active, the same Preview path otherwise), inside the existing coordinated config-update flow, and reject with the structured `InvalidConfigInputError` / `InvalidRepositorySettingsError` family naming the offending model field. GraphQL model fields stay nullable strings—the catalog is discovered at runtime and differs per backend and provider mode, so a static enum is wrong. Work Item creation and each Agent Turn reject a resolved model absent from the backend's current Ready catalog with actionable guidance **before** the Agent Backend CLI is spawned (Step Run reason `agent_model_not_in_catalog`); a Ready backend reporting an empty catalog carries no membership information and does not gate admission. Thinking Level options derive from the selected catalog entry, with no free-text fallback; an incompatible stored level is cleared on model change or marked unavailable. Settings refreshes provider-mode and catalog metadata on every open so an indefinitely cached catalog cannot survive a Harness restart; Recheck Agent Backend remains the explicit atomic refresh.
- **Thinking Levels via `--effort`.** Official levels frozen for v1: `low`, `medium`, `high`, `xhigh`, `max`. When Settings supplies a Thinking Level, every turn passes `--effort <level>`; `null` omits the flag (CLI/model default). `ultracode` is not a Thinking Level in the catalog (workflow mode and version-gated, not a plain effort). Unsupported model×effort combinations surface as ordinary Step Run / CLI failures.
- **Unattended permission skip.** Every turn uses `--dangerously-skip-permissions` (or equivalent bypass mode) so file, shell, and tool use never wait for operator approval mid-turn (ADR 0031). This is parity with Grok (`--yolo`) and Codex (`--sandbox danger-full-access`); containment remains the git worktree plus operator trust in the backend.
- **No `--bare` on lifecycle turns.** Bare mode skips `CLAUDE.md`, hooks, skills, plugins, MCP, and auto memory, and does not read OAuth / keychain credentials (API key only). Lifecycle Agent Turns use full discovery so project instructions and ambient subscription login work. Bare may be reconsidered later only as an explicit CI-oriented mode, not the default.
- **Auto-update disabled under Harness.** The adapter environment forces `DISABLE_AUTOUPDATER` on every inspect and turn spawn so Harness operation cannot replace the CLI underneath active work (same policy as Grok’s `--no-auto-update`).
- **No Session Telemetry in v1.** Session Telemetry is optional (ADR 0033). Claude Code may emit usage/cost on stream or final envelopes; v1 declares the capability unsupported. A stream- or file-backed provider can be added later without a contract change.
- **No Keymaxxer for Claude credentials in v1.** Ambient login or process-environment API key only, matching initial Grok and Codex. Keymaxxer-held Anthropic secrets would be a later optional capability.

Rejected alternatives: Agent SDK or ACP as the primary integration surface; end-of-turn-only Session ID capture; `--continue` for multi-Work-Item concurrency; dual turn path via `claude ultrareview` for review steps; static catalog of pinned dated model IDs only (aliases match operator-facing Claude Code); shipping `ultracode` as a Thinking Level in v1; Keymaxxer-required auth; forcing Claude Code as the harness default.

## Consequences

New or renamed first-party Claude Code model aliases are unavailable in Settings until a Harness release updates the static catalog, and—because selection is catalog-only (issue #838)—there is no free-text escape hatch for pinned, dated, preview, or context-window model strings; an Anthropic-side alias remapping or deprecation surfaces when the operator picks another catalog entry. An operator whose stored model left the catalog (typically after a provider-mode change, since backend-scoped prefs are keyed by the stable backend ID `claude` and are not split by provider mode) sees the stored value marked unavailable in Settings, is refused by the config mutations, and has Work Item creation and Agent Turns rejected with configuration guidance instead of a burned Agent Turn. Bedrock operators with `CLAUDE_CODE_USE_BEDROCK=1` on the harness process see **Claude Code Bedrock** in Settings and must choose a discovered system-defined or application inference profile (friendly names in Settings; executable ID/ARN stored and passed to Claude Code). Failed or empty discovery does not mark Claude Code Unavailable, but Settings block Save until a current profile can be selected after Recheck. Operators must install the `claude` binary and complete ambient auth before Claude Code is Ready; the AWS CLI is not a host prerequisite for Bedrock catalog discovery. Inspect failure yields per-backend Agent Backend Unavailable (ADR 0037), not a harness-wide outage. Host preflight requires `claude` when the harness default or any Repository override selects it. AWS configuration that exists only inside Claude Code settings may leave harness-side profile discovery empty while Claude itself still runs Agent Turns—export Bedrock/AWS on the harness process for the supported discovery path. Implementation follows Codex-parity delivery: adapter package, built-in registry entry, harness runtime wiring, unit and fake-CLI tests, opt-in authenticated live adapter tests, and an optional list-only Bedrock discovery probe that must not invoke billable models. CONTEXT.md gains a **Claude Code** glossary term (stable ID `claude`) when the adapter ships.
