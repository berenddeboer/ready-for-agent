# Explicit Work Item Execution Profile for Implement With

Status: accepted (supersedes the per-Work-Item selection exclusions in ADR 0037 and the blanket model-snapshot rejection in ADR 0035)

Add a distinct `Implement with...` Issue-menu action and `implementWith` command for remote implementation of one Actionable Issue. Its ephemeral `Implement issue #N with...` dialog starts from the Repository's effective Agent Backend and currently resolved backend-scoped model preferences, then lets the operator choose any shipped Agent Backend, a build Agent Model and optional Thinking Level, and either `Same as build` or a distinct review Agent Model and optional Thinking Level. The command always persists those choices as one complete, immutable Explicit Work Item Execution Profile, even when the pre-filled values were not changed, without changing Repository settings or Harness Config.

Ordinary Implement Now, Implement Locally, Queue, Repository Intake, and parent Implement All retain their current behavior: they capture the Repository's effective backend and resolve models from current settings at each Agent Turn. An explicit profile instead remains authoritative through waiting, Start, Retry, Needs Human, process restarts, review, and PR repair; missing catalog entries fail closed without fallback or substitution, and selecting a different profile requires Reset and a new Work Item. `Same as build` is persisted as fallback intent and uses exactly the build model and Thinking Level.

The dialog keeps backend-scoped drafts only while open, uses catalog-only selectors, requires a non-empty catalog, permits a blank required build choice when defaults are unconfigured, and leaves backend switching available after one selection fails. It provides ordinary loading and failure feedback but no recovery, Recheck, Settings detour, fallback, or retry workflow. Submission atomically revalidates Issue eligibility, activates and inspects the chosen backend when necessary, validates catalog membership and the complete profile, and creates nothing on failure. The resulting Work Item detail and history identify the profile as explicit and show its backend, build selection, and review selection.

An unfinished explicit-profile Work Item does not block Repository or Harness default-backend changes because those settings cannot alter its routing or models. Its captured backend remains selected-or-in-use and Active for the Work Item's lifetime. Existing Work Items migrate with no explicit profile and preserve settings-resolved model behavior.

Rejected alternatives: changing Repository defaults as a side effect; persisting a per-Issue preference across attempts; freezing ordinary Work Items; partial per-field overrides; adding custom selection to local, queue, intake, or parent paths; free-text model IDs; silently using current defaults after catalog drift; editing an in-flight profile; and making the dialog browser-addressable.
