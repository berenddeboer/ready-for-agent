# Repositories are identified by Forge, Forge Host, and Project Path

To add GitLab as a second forge (ADR 0043), Repository identity changes from an implied-GitHub owner/name pair to three parts: a **Forge** (`github` or `gitlab`), a **Forge Host** (`github.com` for GitHub, or a self-managed instance such as `git.drupalcode.org`), and a single **Project Path** — `owner/name` for GitHub, a group or nested subgroup path for GitLab (e.g. `project/oauth_client`). Identity is case-insensitive on the path with display casing preserved. A git remote's hostname is not authoritative for the Forge Host — Drupal's GitLab serves SSH as `git.drupal.org` but the API as `git.drupalcode.org` — so forge identity is guessed from the remote when a Repository is added, verified against the Forge API before saving, and correctable in Repository settings; changing it is rejected while any Work Item exists for the Repository, since Work Items record issue and pull request numbers whose meaning depends on the forge.

**Considered Options.** A forge + host + owner/name pair keeps the two-segment shape and the smallest migration, but bakes in "GitLab projects are exactly two segments", which is false for nested GitLab groups generally. A full clone URL as identity was rejected: one project has too many spellings (SSH vs HTTPS, trailing `.git`, case), making identity comparison fuzzy string matching — Forge Host plus Project Path is its normalized form.

**Consequences.** The `github_owner`/`github_repo` columns, GraphQL fields, Keymaxxer credential account strings, and every `owner/name`-shaped service argument migrate to the three-part identity. The Keymaxxer credential account for GitLab becomes `<forge-host>/<project-path>`. GitHub Enterprise hosts and additional GitLab instances become representable without another remodel.
